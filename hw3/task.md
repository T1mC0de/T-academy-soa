## Архитектура системы

Система состоит из двух микросервисов с раздельными базами данных:

```text
Client (REST) ──→ Booking Service ──(gRPC)──→ Flight Service
                       │                          │
                   PostgreSQL                PostgreSQL + Redis
```

### Booking Service

Сервис управления бронированиями:

- предоставляет REST API для клиентов;
- хранит бронирования в собственной базе PostgreSQL;
- вызывает Flight Service по gRPC.

### Flight Service

Сервис управления рейсами и местами:

- предоставляет gRPC API для межсервисного взаимодействия;
- хранит рейсы и резервации в собственной базе PostgreSQL;
- начиная с пункта 7, кеширует данные в Redis.

> Каждый сервис должен использовать собственную базу данных.

## Общие требования

- Все сервисы запускаются одной командой:

  ```bash
  docker-compose up
  ```

- Миграции баз данных применяются автоматически при старте.
- `.proto`-файлы и контракты проектируются студентом самостоятельно.
- Допускается использование любого языка программирования и фреймворка.

> **Примечание.** Задание намеренно не содержит полной спецификации

> таблиц студент определяет самостоятельно — это часть задания.

## Блок 1: базовая архитектура и интеграция — 1–4 балла

### 1. gRPC-контракт Flight Service — 1 балл

Необходимо самостоятельно спроектировать `.proto`-файлы для Flight Service.

#### Обязательные методы

| Метод | Описание |
|---|---|
| `SearchFlights` | Поиск рейсов по маршруту и дате |
| `GetFlight` | Получение информации о рейсе по ID |
| `ReserveSeats` | Резервирование мест для бронирования |
| `ReleaseReservation` | Отмена резервирования и возврат мест |

#### Требования

- Ключевые методы контракта отражают бизнес-операции предметной области
  (поиск и резервирование), а не являются обёртками над таблицами.
- Используется кодогенерация из `.proto` с помощью `protoc`.
- Для дат используется `google.protobuf.Timestamp`.
- Для статусов используются `enum`.
- Для бизнес-ошибок используются стандартные gRPC-коды:
  `NOT_FOUND`, `RESOURCE_EXHAUSTED` и другие подходящие коды.

### 2. ER-диаграмма в 3NF — 1 балл

Необходимо спроектировать схему данных для обоих сервисов.

#### Основные сущности

**Flight** *(Flight Service)* — рейс:

- авиакомпания;
- маршрут: аэропорты вылета и прилёта в формате IATA-кодов
  (например, `VKO`, `LED`);
- время вылета и прилёта;
- общее и доступное количество мест;
- цена билета;
- статус: `SCHEDULED`, `DEPARTED`, `CANCELLED`, `COMPLETED`.

Комбинация номера рейса и даты вылета уникальна. Например, `SU1234` на
`2026-04-01` — это один конкретный рейс.

**SeatReservation** *(Flight Service)* — резервация мест:

- привязана к конкретному рейсу и бронированию из Booking Service;
- содержит количество зарезервированных мест;
- имеет статус: `ACTIVE`, `RELEASED`, `EXPIRED`.

Одному бронированию соответствует ровно одна резервация.

**Booking** *(Booking Service)* — бронирование:

- данные пассажира;
- ссылка на рейс из Flight Service;
- количество мест;
- стоимость;
- статус: `CONFIRMED`, `CANCELLED`.

#### Требования к диаграмме

- Формат на выбор: **dbdiagram.io**, **draw.io**, **PlantUML** или **Mermaid**.
- Схема соответствует третьей нормальной форме (3NF).
- Определены ограничения целостности данных:
  - доступное количество мест не может быть отрицательным;
  - общее количество мест и цена строго положительны;
  - заданы остальные необходимые ограничения и уникальные ключи.

### 3. PostgreSQL и реализация сервисов — 1 балл

- Подключены две базы PostgreSQL — отдельная база для каждого сервиса.
- Миграции выполняются с помощью Flyway, Liquibase или другого аналога.
- В Booking Service реализованы REST API-эндпоинты.
- В Flight Service реализован gRPC-сервер с методами из пункта 1.
- Подробное описание методов приведено в [приложении](#приложение-1-спецификация-методов).

### 4. Межсервисное взаимодействие по gRPC — 1 балл

Booking Service вызывает Flight Service по gRPC:

- при создании бронирования;
- при отмене бронирования.

#### Обязательный сценарий создания бронирования

1. `Booking Service → GetFlight` — получить информацию о рейсе, включая цену.
2. `Booking Service → ReserveSeats` — зарезервировать места.
   Операция должна атомарно проверить доступность мест и создать резервацию.
3. При успешной резервации зафиксировать цену:
   `total_price = seat_count × flight.price`.
4. Создать запись о бронировании в собственной базе данных.
5. При ошибке не создавать бронирование и вернуть ошибку клиенту.

## Блок 2: транзакции, аутентификация и кеширование — 5–7 баллов

### 5. Транзакционная целостность — 1 балл

#### Flight Service

- Уменьшение `available_seats` и создание `SeatReservation` выполняются
  в одной транзакции.
- Для предотвращения двойного бронирования последних мест используется
  `SELECT FOR UPDATE`.
- Возврат `available_seats` и обновление статуса резервации при отмене
  выполняются в одной транзакции.

#### Booking Service

- Если gRPC-вызов `ReserveSeats` завершился ошибкой, бронирование
  не создаётся.
- Не допускаются частично применённые изменения.

### 6. Аутентификация межсервисных вызовов — 1 балл

Необходимо реализовать аутентификацию gRPC-вызовов между сервисами.
Выберите один из подходов:

- API key в gRPC metadata;
- service JWT в metadata;
- Basic Auth (логин и пароль) в metadata.

#### Требования

- Flight Service проверяет аутентификацию для всех методов.
- При отсутствии или невалидных credentials возвращается gRPC-ошибка
  `UNAUTHENTICATED`.
- Credentials передаются через переменные окружения контейнера.

### 7. Redis для кеширования — 1 балл

Redis используется во Flight Service для кеширования.

| Данные | Пример ключа | TTL |
|---|---|---|
| Информация о рейсе | `flight:{id}` | 5–10 минут |
| Результаты поиска | `search:{origin}:{destination}:{date}` | 5–10 минут |

#### Требования

- Redis запускается в `docker-compose`.
- Реализована стратегия **Cache-Aside**:
  проверка кеша → при cache miss запрос к БД → запись в кеш с TTL.
- У всех ключей задан TTL; бесконечный кеш не используется.
- Кеш инвалидируется после мутаций (`UpdateFlight`, `ReserveSeats`,
  `ReleaseReservation`), чтобы не возвращать устаревшие данные.
- В логах присутствуют события `cache hit` и `cache miss`.

## Блок 3: отказоустойчивость — 8–10 баллов

### 8. Retry при вызовах Flight Service — 1 балл

Booking Service реализует retry для gRPC-вызовов к Flight Service.

#### Требования

- Максимум 3 попытки.
- Exponential backoff, например: `100 ms`, `200 ms`, `400 ms`.
- Повторять запрос только при ошибках:
  - `UNAVAILABLE`;
  - `DEADLINE_EXCEEDED`.
- Не выполнять retry при ошибках:
  - `INVALID_ARGUMENT`;
  - `NOT_FOUND`;
  - `RESOURCE_EXHAUSTED`.
- Для мутирующих операций (`ReserveSeats`) обеспечена идемпотентность:
  повторный вызов с тем же `booking_id` не создаёт дубликат резервации.

### 9. Redis в кластерном режиме — 1 балл

Redis запускается в отказоустойчивой конфигурации внутри `docker-compose`.
Необходимо выбрать один вариант:

- **Sentinel:** мастер, реплика и Sentinel;
- **Cluster:** минимум 3 мастер-ноды.

Код приложения использует Redis-клиент с поддержкой выбранного режима
(`Sentinel` или `Cluster`).

### 10. Circuit Breaker — 1 балл

Booking Service реализует паттерн **Circuit Breaker** для вызовов к
Flight Service.

#### Состояния Circuit Breaker

**CLOSED** — штатная работа, запросы выполняются. При накоплении ошибок
(например, 5 ошибок подряд или превышение порога за временное окно) происходит
переход в `OPEN`.

**OPEN** — запросы к Flight Service немедленно завершаются ошибкой без
реального вызова. Через заданный таймаут (например, 10–30 секунд) происходит
переход в `HALF_OPEN`.

**HALF_OPEN** — пропускается один пробный запрос:

- при успехе переход в `CLOSED`;
- при ошибке возврат в `OPEN`.

#### Требования

- Circuit Breaker реализован как interceptor или middleware на стороне
  Booking Service, а не внутри бизнес-логики.
- Порог ошибок, таймаут и размер окна настраиваются через переменные окружения.
- В логах видны переходы между состояниями:
  `CLOSED → OPEN`, `OPEN → HALF_OPEN` и другие.
- В состоянии `OPEN` клиент получает осмысленную ошибку
  (например, `503 Service Unavailable`), а не таймаут.

## Приложение 1. Спецификация методов

### Booking Service — REST API

#### Поиск рейсов

```http
GET /flights?origin=SVO&destination=LED&date=2026-04-01
```

Проксирует вызов `Flight Service (SearchFlights)`.

- `origin` и `destination` обязательны;
- `date` опционален;
- возвращается список рейсов со статусом `SCHEDULED`.

#### Получение рейса

```http
GET /flights/{id}
```

Проксирует вызов `Flight Service (GetFlight)`. Если рейс не найден,
возвращается `404`.

#### Создание бронирования

```http
POST /bookings
```

Тело запроса содержит:

```json
{
  "user_id": "...",
  "flight_id": "...",
  "passenger_name": "...",
  "passenger_email": "...",
  "seat_count": 1
}
```

Перед созданием бронирования система обязана:

1. Получить информацию о рейсе через `GetFlight`.
2. Зарезервировать места через `ReserveSeats`.
3. Зафиксировать стоимость:
   `total_price = seat_count × flight.price`.
4. Создать бронирование со статусом `CONFIRMED`.

Если резервирование не удалось, бронирование не создаётся.

#### Получение бронирования

```http
GET /bookings/{id}
```

Возвращает бронирование по ID. Если бронирование не найдено, возвращается `404`.

#### Отмена бронирования

```http
POST /bookings/{id}/cancel
```

1. Проверить, что бронирование имеет статус `CONFIRMED`.
2. Вызвать `Flight Service (ReleaseReservation)` для возврата мест.
3. Установить статус бронирования `CANCELLED`.

> При реализации на 3 балла проверку результата `ReleaseReservation` можно
> не выполнять.

#### Список бронирований

```http
GET /bookings?user_id=X
```

Возвращает список бронирований пользователя.

### Flight Service — gRPC

Контракт проектируется студентом. Ниже описано обязательное поведение методов.

#### `SearchFlights`

Ищет рейсы по маршруту (`origin`, `destination`) и опционально по дате.
Возвращает список рейсов со статусом `SCHEDULED`.

#### `GetFlight`

Возвращает рейс по ID. Если рейс не найден, возвращает `NOT_FOUND`.

#### `ReserveSeats`

Принимает `flight_id`, `seat_count` и `booking_id`.

- атомарно уменьшает `available_seats`;
- создаёт `SeatReservation`;
- при недостатке мест возвращает `RESOURCE_EXHAUSTED`.

#### `ReleaseReservation`

Принимает `booking_id`, находит активную резервацию, возвращает места и
переводит резервацию в статус `RELEASED`.
